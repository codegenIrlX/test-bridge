# Конфигурация и запуск

Платформа читает настройки из `config.yaml`, а пароль PostgreSQL и токен API — из `secrets.yaml`. Перед запуском создайте `secrets.yaml` по образцу `secrets.example.yaml` и задайте собственные значения. Не добавляйте этот файл в Git и не передавайте его в контекст сборки образа.

В обоих файлах раздел `default` задаёт общие значения, а раздел выбранного окружения переопределяет их. Вложенные объекты объединяются по ключам. Окружение выбирается переменной `METRICS_SRV_ENV`; без неё используется `development`. Оба файла должны содержать раздел выбранного окружения, даже если он пуст. При отсутствии или неверном значении обязательных параметров процесс завершает запуск с ошибкой.

`config.yaml` содержит адреса и порты PostgreSQL и Redis, путь к архивам, пределы размера и количества файлов, а также интервал работы Scheduler. `secrets.yaml` содержит `database.password` и `api.token`. В Docker файл конфигурации монтируется только для чтения. Однократный контейнер читает Compose secret от имени root и копирует его в tmpfs с владельцем приложения и правами `0400`; остальным процессам tmpfs доступен только для чтения. Локально приложение читает `secrets.yaml` из рабочего каталога; внутри контейнера используется `/run/secrets/secrets.yaml`.

После настройки файлов запустите платформу:

```sh
docker compose up -d --build
```

Compose запускает PostgreSQL, Redis, миграции и три процесса приложения. API доступен на порту 8000 хоста. Данные PostgreSQL, очередь Redis и входящие архивы хранятся в именованных томах. Временные файлы для инициализации PostgreSQL создаются в отдельном томе tmpfs и не включаются в образ. Служебный контейнер удерживает оба тома tmpfs смонтированными между завершением однократной подготовки и запуском потребителей. Для запуска требуются Linux-контейнеры.

## Первый запуск с Alembic

Первая ревизия создаёт схему на пустой PostgreSQL 17. Для чистого dev-стенда
выберите новый идентификатор проекта Compose. У проекта будут отдельные тома
PostgreSQL, Redis и архивов. Если старый стенд занимает опубликованные порты,
остановите его перед запуском нового.

```sh
docker compose -p testbridge-orm-dev up -d --build
docker compose -p testbridge-orm-dev ps -a
```

Сервис `migrate` применяет `upgrade head` после готовности PostgreSQL.
Успешное завершение `migrate` разрешает запуск API, Scheduler и Processor.
При ошибке миграции проверьте `docker compose -p testbridge-orm-dev logs migrate`.

Для явного сброса одноразового стенда проверьте его имя и состав томов командой
`docker volume ls --filter label=com.docker.compose.project=testbridge-orm-dev`.
Команда `docker compose -p testbridge-orm-dev down --volumes` удалит данные БД,
очередь и архивы этого проекта. Следующий `up` создаст пустой стенд. Обычная
команда `python -m metrics_srv migrate` применяет ревизии к указанной в настройках БД.

## Обслуживание

После изменения `secrets.yaml` подготовьте копию командой `docker compose run --rm --no-deps secret-bootstrap`, затем перезапустите процессы приложения командой `docker compose restart api scheduler processor`: они читают настройки при старте. После перезапуска Docker daemon или хоста повторно выполните `docker compose up -d`: tmpfs может очиститься, а обычный `docker compose restart` не запускает однократные контейнеры подготовки.

Пароль из YAML используется при первоначальном создании базы. Изменение YAML не меняет пароль существующего пользователя PostgreSQL: ротация должна отдельно обновить пароль в БД и секрет приложения. Именованные тома не заменяют резервное копирование.
