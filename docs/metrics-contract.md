# Контракт аналитики Allure

Документ фиксирует решения для реализации плана [аналитики прогонов](plan/metrics-development/plan.md). Он описывает целевое поведение; наличие документа не подтверждает, что возможности уже работают.

## Прогон и загрузка

Импорт — единица обработки одного принятого архива и одновременно единица прогона для аналитики. Это не гарантирует, что архив содержит все результаты сборки: полноту внешней сборки по отдельному ZIP определить нельзя. `imports.status` отражает обработку архива, а не результат тестов.

`POST /api/v1/imports` сохраняет прежние `multipart/form-data` с полем `file`, сервисный Bearer-токен, асинхронный ответ `202` и существующий контракт ответа. Добавочные текстовые поля `project`, `job`, `buildNumber`, `buildUrl`, `revision` необязательны: старый Jenkins продолжает отправлять только `file`. Пустые отсутствующие метаданные хранятся как `NULL`. Строки должны иметь ограниченную длину, проверяться до регистрации и не попадать в сообщения об ошибках и логи. Поля передаются как данные CI и не удостоверяют личность проекта. URL используется как ссылка в данных, не как адрес для серверного запроса.

Необязательный `Idempotency-Key` позволяет CI безопасно повторять отправку одного и того же архива. Сервис сохраняет ключ и SHA-256 архива рядом с импортом; уникальный индекс обеспечивает атомарность одновременных отправок. Совпадение ключа и хеша возвращает идентификатор уже принятого импорта; повтор с тем же ключом и другим содержимым или другими метаданными — `409` в общем формате ошибок. Временные и лишние файлы после гонки регистрации удаляются. Без ключа каждая загрузка создаёт отдельный импорт, как и прежде. Ключ не является именем метрики или её меткой. Детали передачи полей и повтора должны совпадать с реализацией OpenAPI и Jenkins.

Проект идентифицируется предоставленным CI значением `project`; старые импорты остаются без проекта. `job` и `buildNumber` помогают найти сборку, но не заменяют ключ идемпотентности. Не следует выводить проект из названия теста или произвольно объединять данные без идентификатора. Идентификаторы тестов и шагов, имена заданий, номера сборок, URL и ревизии хранятся в PostgreSQL, но не используются как метки метрик.

Предлагаемые поля схемы — все новые поля допускают `NULL`, чтобы не изменять исторические записи:

| Таблица | Поля | Назначение |
| --- | --- | --- |
| `imports` | `project`, `job`, `build_number`, `build_url`, `revision` | Метаданные CI |
| `imports` | `idempotency_key`, `archive_sha256` | Идентификатор запроса и хеш содержимого для безопасного повтора; частичный уникальный индекс по непустому ключу |
| `imports` | `processing_started_at`, `processing_finished_at` | Границы последней обработки импорта для измерения времени |
| `test_results` | `status`, `allure_uuid`, `history_id`, `test_case_id`, `full_name`, `labels`, `parameters` | Результат и идентификаторы Allure; `labels` сохраняет выбранные повторяющиеся значения |
| `test_steps` | `status` | Статус шага Allure |

Имена и ограничения полей должны соответствовать итоговой миграции; `labels` может храниться в JSONB или в связанной таблице с сохранением повторов. Новый индекс не должен конфликтовать со старыми строками с `NULL`. Для новой схемы и существующей БД необходимы одинаковые комментарии колонок.

## Данные Allure

Разбираются только исходные `*-result.json`. `*-container.json`, фикстуры и вложения остаются вне объёма. Названия, порядок, время и иерархия шагов сохраняют существующую семантику. Результат и его шаги дополняются полем `status`; для теста сохраняются необязательные `uuid`, `historyId`, `testCaseId`, `fullName` и выбранные метки `suite`, `parentSuite`, `subSuite`, `tag`, `framework`, `language`. Повторяющиеся метки нельзя без указания правила молча отбрасывать: хранение должно сохранять все значения или отдельно документировать ограничения. Значения меток и идентификаторы — данные Allure, не разрешённые автоматически метки метрик.

В аналитике известны `passed`, `failed`, `broken`, `skipped` и `unknown`; отсутствующее или нераспознанное значение относится к `unknown`. Приводить его к `passed` нельзя. Время необязательно; длительность в секундах равна `(stop - start) / 1000`, только когда оба значения существуют и `stop >= start`. Отсутствующие и некорректные интервалы исключаются из суммы и числа измерений длительности, но не из числа результатов.

Повторы теста внутри одного архива считаются отдельными **попытками**. Для **итоговых тестов** группируются результаты с одинаковым непустым `historyId` внутри одного импорта; без `historyId` каждый результат остаётся самостоятельным. Выбирается результат с максимальным `stop`, затем `start`, затем порядком результата; отсутствующее время сортируется раньше имеющегося. Такое правило детерминировано, но не доказывает фактическую последовательность, если адаптер не передал время. Две разные сущности нельзя объединять только по имени или `fullName`.

Итог прогона определяется по итоговым тестам с приоритетом `broken`, `failed`, `unknown`, `skipped`, `passed`. Прогон без результатов имеет статус `unknown`. Параметры с режимом `hidden` или `masked` сохраняются без значения.

## Правила агрегации и экспорта

Агрегаты результатов строятся по зафиксированным данным `completed` импортов; неуспешный или ещё обрабатываемый импорт не даёт частичных результатов. Для количества тестов различаются попытки и итоговые тесты. Длительности считаются отдельно с числом валидных измерений; среднее — сумма длительностей, делённая на это число. При нулевом знаменателе среднее и доля успеха отсутствуют, а не равны нулю.

Число импортов по состоянию — текущий срез: неуспешный импорт может вернуться в `pending`, поэтому такой показатель не является монотонным счётчиком. Время обработки рассчитывается по сохранённым моментам начала и завершения обработки, а не из времён тестов; отсутствующие интервалы не учитываются. Состояние очереди отражает текущий срез BullMQ и отдельно показывает недоступность источника: подмена ошибки нулём скрыла бы проблему.

Метрики результатов выводятся как агрегаты текущих сохранённых записей PostgreSQL, а не как инкременты памяти отдельного worker. Повтор одной задачи и рестарт процесса не создают новые записи и не увеличивают агрегат. Изменение или удаление исторических данных может уменьшить такой агрегат; при его использовании как Prometheus counter необходимо сохранить неизменность учтённых записей или явно учитывать сбросы. Если Collector запрашивает несколько экземпляров API, он не должен суммировать одинаковые снимки одного источника. Запросы для трендов должны учитывать интервал опроса и перезапуски.

Набор меток ограничивается фиксированными статусами и, при необходимости, `project` и `suite` из конфигурационных списков разрешённых значений. Неизвестные значения группируются в `other`, отсутствующие — в `unknown`; число значений ограничено конфигурацией. Перекрёстное произведение разрешённых значений должно быть приемлемым для VictoriaMetrics. Запрещены имена тестов и шагов, `uuid`, `historyId`, номера сборок и другие неограниченные значения в метках. Сами исходные значения сохраняются для анализа в PostgreSQL.

Collector получает метрики сервиса, передаёт их в VictoriaMetrics, а Grafana читает агрегаты из VictoriaMetrics. PostgreSQL остаётся источником деталей и восстановления агрегатов после перезапуска приложения. Доставка не считается проверенной по одной готовности контейнеров: необходимо проверить доступность экспорта, наличие временных рядов в VictoriaMetrics и панели Grafana.

Минимальный контракт имён для согласования с дашбордом:

| Метрика | Тип и измерения | Значение |
| --- | --- | --- |
| `testbridge_test_results` | gauge; `status`, `kind`, разрешённые `project` и `suite` | Количество результатов или итогов; `kind` — `attempt` либо `final` |
| `testbridge_test_duration_seconds_sum`, `testbridge_test_duration_seconds_count` | gauge; те же измерения | Сумма длительностей и число результатов с корректным временем |
| `testbridge_imports` | gauge; `status` | Текущие количества импортов по состоянию обработки |
| `testbridge_runs` | gauge; `status` | Исход завершённых прогонов по итоговым тестам |
| `testbridge_import_processing_seconds_sum`, `testbridge_import_processing_seconds_count` | gauge | Сумма времени и число измерений обработки |
| `testbridge_queue_jobs` | gauge; `state` из фиксированного набора | Текущие количества заданий очереди |

Для каждой опубликованной метрики формат и точные метки должны совпадать с фактическим экспортом и запросами Grafana. Ошибка чтения источника должна делать соответствующий scrape неуспешным либо сопровождаться отдельным показателем доступности, а не заменяться нулевыми данными.

## Миграция и проверка

Текущий `migrate` исполняет `schema.sql`, где таблицы создаются через `CREATE TABLE IF NOT EXISTS`: новые колонки для уже существующей БД требуют отдельных идемпотентных изменений схемы. Существующие данные и связи сохраняются, новые поля для старых записей остаются `NULL`, описания колонок хранятся в комментариях PostgreSQL. Уже удалённые архивы не позволяют восстановить несохранённые статусы и метки.

Проверки должны охватить миграцию заполненной БД и повторный запуск миграции; старый запрос без метаданных; новые метаданные и OpenAPI; одновременную повторную отправку ключа, конфликт содержимого и повтор processor; отсутствующие и нераспознанные статусы, отрицательные интервалы, вложенные шаги и повторы с неполным временем. После этого проверяются доставка через Collector, сохранение рядов после перезапусков, отсутствие двойного учёта и данные реального Jenkins-прогона на дашборде. Результат обработки архива и результат тестов проверяются отдельно.
