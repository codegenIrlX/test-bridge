# Перевод БД TestBridge на SQLAlchemy ORM и Alembic

Цель — новая версия схемы PostgreSQL 17, одна исходная ревизия Alembic
и запросы на SQLAlchemy 2.x с драйвером psycopg 3. Проект ещё не в production.
Начинаем с пустой БД. Перенос, stamp и поддержка прежней схемы не требуются.
Переиспользуем текущий контракт загрузки ZIP, чтения статуса и повтора для Jenkins.
Если контракт заменяется, вместе обновляются маршруты, DTO, OpenAPI, тесты и Jenkins.

Аудит обнаружил запуск SQL без версий, отдельный INSERT на каждый результат
и шаг и зависимость обработки от advisory-блокировки одного соединения.
Текущие тесты с подменами не подтверждают транзакции и блокировки на PostgreSQL.

Источник схемы после перехода — граф Alembic. Исходная ревизия содержит
собственное описание схемы, а метаданные моделей используются для сравнения.
Имена: pk__table, fk__table__columns__referenced_table, uq__table__columns,
ck__table__purpose, ix__table__columns. Сервис migrate стартует после готовности
PostgreSQL, приложение ждёт успешного завершения. UUID-первичные ключи трёх
сущностей определяет общий mixin. Откат исходной ревизии уничтожает данные,
поэтому его проверяют только на одноразовой БД.

## Результаты проверки

- Полный pytest с временной PostgreSQL 17: 46 прошли, 2 POSIX-теста пропущены
  на Windows. Интеграционные сценарии проверили цикл миграций, схему,
  конкурентную блокировку, откат записи, повтор импорта и очистку ZIP.
- Ruff для `metrics_srv`, `tests` и `deploy` прошёл. Общий `ruff check .`
  по-прежнему сообщает 21 исходное замечание в примерах скилла `pytest-testing`.
- На чистом Compose-проекте собран образ и проверена ревизия `0001_initial`
  в установленном пакете из другого рабочего каталога. Через HTTP проверены
  OpenAPI, отказ без авторизации, загрузка ZIP, завершение импорта, очистка
  и повтор неуспешного импорта.
- При намеренном завершении мигратора с кодом 23 API, Scheduler и Processor
  остались в состоянии `created`. Проверки выполнялись на отдельных томах
  с тестовыми данными.
