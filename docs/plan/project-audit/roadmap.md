# TestBridge — аудит и дорожная карта

Дорожная карта охватывает надёжность импорта из Jenkins, восстановление после сбоев, доставку агрегатов до VictoriaMetrics и первую панель Grafana. Итоги проверок собраны в разделе «Продолжение после запуска ORM».

## Что показал аудит

Проверена ветка `feature/metrics-development`, коммит `5a3385c`. В ней есть приём ZIP, отслеживание статуса и ручной повтор через API v1, обработка через BullMQ и запись результатов в PostgreSQL. Alembic управляет схемой этой ветки. Аналитика из `7103250` удалена в `caea813`. Схема на момент аудита хранит имена, время и вложенность шагов. Для аналитики понадобятся статусы Allure и привязка к сборкам Jenkins. Модели доступны через `git show 5a3385c:metrics_srv/models.py`. [Архитектура импорта](../../architecture.md)

| Приоритет | Находка и последствие |
|---|---|
| **P1 · Повтор отправки** | Если Jenkins потеряет ответ `202` и отправит тот же ZIP снова, сервис создаст второй импорт. Два запроса с одинаковым ZIP дали два UUID в локальной проверке с подменой БД. Автоповтор доставки и аналитика требуют дедупликации. [Приём ZIP](../../../metrics_srv/api.py#L131) |
| **P1 · Очистка диска** | При сбое Redis и наличии ожидающего задания Scheduler пропускает очистку. Если удаление 100 старейших ZIP постоянно завершается ошибкой, они занимают всю выборку и задерживают удаление остальных. ZIP неуспешных импортов хранятся бессрочно. [Scheduler](../../../metrics_srv/background.py#L40) · [Очистка ZIP](../../../metrics_srv/repository.py#L168) |
| **P1 · Общий том** | Compose монтирует архивы в `/data/imports`, а конфигурация разрешает другой путь. При таком переопределении API может вернуть `202` после записи в собственный контейнер. Processor в своём контейнере этот ZIP не увидит. [Настройка пути](../../../metrics_srv/config.py#L111) · [Монтирование тома](../../../compose.yaml#L108) |
| **P2 · Некорректные данные** | На момент аудита парсер пропускал значение времени за пределами PostgreSQL `BIGINT`. Интеграционный тест в `5a3385c` фиксировал откат записи и статус `processing` после ошибки БД. Повреждённый deflate тоже мог расходовать попытки обработки вместо диагностируемого `failed`. [Парсер](../../../metrics_srv/parser.py) |
| **P2 · Восстановление** | После перезапуска хоста требуется повторный `docker compose up -d` для подготовки секретов в tmpfs. В репозитории нет CI-проверки с реальными PostgreSQL и Redis, а текущие тесты очереди используют подмены. [Регламент запуска](../../configuration.md#обслуживание) · [Тесты очереди](../../../tests/test_board_queue.py#L34) |

Хранить в PostgreSQL время следующей попытки очистки проблемного файла и откладывать её на пять минут. Зависимости отсутствуют. Проверка — очистка при недоступном Redis и прогресс после ошибок удаления первых ста ZIP.

- [x] **Tester · Регрессии.** Владелец `tests/`. После получения интерфейсов проверить ошибки архива и границу допустимого времени, загрузку конфигурации, недоступность Redis и повтор удаления ZIP. Сохранять пропуски для тестов, требующих недоступной инфраструктуры.

### Исходная дорожная карта аудита

- [x] **1. Developer и Tester · Стабилизировать импорт.** Область — приложение, Compose и тесты. Проверять путь к общему тому при запуске Compose. Отклонять непредставимые в БД данные и повреждённые ZIP после первой попытки, сохраняя архив и безопасную причину отказа. Приёмка — отключение Redis, 100 неудаляемых ZIP, неверный путь и повреждённый архив воспроизводятся тестами.

Jenkins формирует стабильный ключ для сборки и повторно отправляет те же байты ZIP. Уникальность ключа обеспечивает PostgreSQL. Тот же ключ и SHA-256 возвращают прежний `importId`, другой ZIP с тем же ключом получает `409`. Запросы только с `file` сохраняют текущее поведение. Приёмка — повтор после потерянного ответа, параллельные POST, один импорт в БД и сверка OpenAPI.

Приёмка — каждый принятый ZIP доходит до конечного статуса, результаты записываются один раз, успешный ZIP удаляется после фиксации. Дополнительно проверить холодный запуск, восстановление PostgreSQL и ожидающих ZIP из копии, видимость возраста очереди и свободного места. Для пилота принять срок хранения неуспешных ZIP **7 дней** с ручным повтором в этот период. После удаления ZIP сохранить запись об импорте и возвращать `409` на повтор.
- [ ] **4. Architect, Developer и Tester · Довести аналитику до VictoriaMetrics после пилота.** Область — контракт данных, модели, новые ревизии Alembic, экспорт и тесты. Внутри одного импорта группировать итоги по непустому `historyId`, выбирать последний результат по `stop`, затем `start` и порядку записи. Без `historyId` считать результат отдельно. Экспортировать количество прогонов, статусы и длительность из PostgreSQL через OpenTelemetry Collector. Приёмка — агрегаты совпадают с контрольной выборкой PostgreSQL и остаются точными после повторной доставки и перезапуска. Идентификаторы тестов и сборок хранить в PostgreSQL, а набор меток метрик ограничить.
- [ ] **5. Developer, Tester и Reviewer · Добавить Grafana после приёмки экспорта.** Область — конфигурация дашборда, документация и проверки. ### Продолжение после запуска ORM · 17 ноября 2026

Цель — подтвердить приём результатов одной QA-джобы и довести аналитику прогонов до VictoriaMetrics, затем Grafana. Стенд `testbridge-orm` поднят с ревизией `0001_imports_orm`; в начале пилота в БД была одна завершённая синтетическая загрузка. Эксплуатационные сценарии с остановкой компонентов проводят на отдельных томах. Развитие схемы идёт новыми ревизиями с сохранением импортов. [Первый запуск](../first-run/compose.md)

#### Подготовка эксплуатационного этапа

Локальные изменения и регрессионные проверки можно подготовить отдельно от запуска Jenkins. Сценарии отказа и развёртывание изменений выполняются на отдельном экземпляре после пилота.

- [x] **Developer · Хранение failed ZIP.** Ревизия `0002_failed_archive_retention` фиксирует время перехода в `failed`. Для старых failed-записей срок начинается после миграции. Scheduler очищает просроченные ZIP под блокировкой строки и сохраняет историю. При сбое удаления повтор откладывается, после удаления ручной retry возвращает 409.
- [x] **Developer · Сборка и Linux CI.** Добавлены фиксированные зависимости, Jenkinsfile TestBridge и изолированный Compose для CI. На Windows нормализованы признаки исполняемых файлов Python внутри CI-образа. Linux-прогон на PostgreSQL 17 и Redis 7 прошёл Ruff, 75 тестов и импорт через очередь. Временные ресурсы удалены.
- [x] **Tech-lead · Наблюдение.** Scheduler раз в минуту пишет возраст старейшего незавершённого импорта и свободное место независимо от Redis. Покрыты нормальные показания и частичный отказ диска. Ошибки и отложенные удаления видны в журнале.
- [x] **Tester · Регрессии хранения.** На PostgreSQL 17 проверены первая попытка, семидневная граница, сохранение истории, сбой удаления, ручной повтор и обратимость ревизии.

## Проверки и условия

- **В этом аудите** прошли 14 тестов парсера и конфигурации, Ruff для `metrics_srv`, `tests` и `deploy`, а также `docker compose config --quiet`. Общий `ruff check .` показал 21 замечание в примерах скилла `pytest-testing`.
- **Полный прогон ограничен окружением.** При аудите `5a3385c` для сбора всех тестов не хватило SQLAlchemy и Alembic. Docker daemon вернул `permission denied`, поэтому живые проверки PostgreSQL, Redis, Compose и Jenkins не выполнялись. Результаты предыдущего прогона с временной PostgreSQL 17 доступны через `git show 5a3385c:docs/plan/database-refactoring/alembic-sqlalchemy.md`.
- **Для пилота согласована отдельная пустая БД.** Перед обновлением прежнего стенда провести инвентаризацию его схемы и томов. Если данные нужны, проверить перенос на копии. Начальная ревизия Alembic в `5a3385c` рассчитана на пустую БД, а для восстановления ранее несохранённых полей понадобятся исходные архивы.
