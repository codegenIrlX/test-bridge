# Предложение: аналитика прогонов Jenkins

Документ содержит предложенный состав панелей для согласования. Панели и новые источники ещё не реализованы и не проверены.

## Проекты и данные

Jenkins передаёт при загрузке `project` и `job` со значением `JOB_NAME`, например `testbridge-validation-20261115`, а также `buildNumber`, `buildUrl` и `revision`. `JOB_NAME` сохраняет путь задания внутри папок Jenkins. Для нескольких серверов Jenkins потребуется отдельный стабильный идентификатор сервера: совпадающие `JOB_NAME` сами по себе не различают задания на разных серверах. До его введения предполагается один сервер Jenkins.

API уже принимает эти поля необязательно, поэтому существующие отправители продолжают работать. Отправитель использует стабильный для конкретной сборки ключ идемпотентности; повтор с тем же ключом требует идентичные архив и метаданные. При новом ZIP с другим содержимым сервер возвращает `409`. Старые импорты без проекта остаются в группе «Неизвестный проект»: восстановить отсутствующие сведения автоматически нельзя.

Сейчас Prometheus-метрики ограничивают `project` и `suite` списками разрешённых значений в конфигурации; при пустом списке они объединяются в `other`. Поэтому фильтр проектов нового аналитического дашборда предлагается строить по сохранённому `imports.project` в PostgreSQL, а не по меткам VictoriaMetrics. Названия тестов не добавляются в метки метрик.

PostgreSQL уже хранит имена тестов, связи с импортом, статусы, `history_id`, временные отметки и метки Allure. Для запросов Grafana предлагается отдельный пользователь БД с правом `SELECT` только на выделенные представления аналитики. Доступ к источнику, учётной записи Grafana и панели должен быть ограничен администраторами платформы; нельзя выдавать Grafana пароль владельца БД или права на изменение данных. Предоставление проектной изоляции как механизма авторизации в этот вариант не входит: фильтр дашборда сам по себе доступ не ограничивает.

## Общие правила расчётов

- Выбор периода — по `imports.created_at`, времени приёма архива; это время не равно началу тестов или всей сборки Jenkins. Для конкретного прогона доступна ссылка на сборку, если она передана.
- В аналитике участвуют только завершённые импорты. Импорт отражает один принятый архив; его полноту относительно всей сборки проверить нельзя.
- По умолчанию используется итоговая попытка теста: в рамках одного импорта результаты с одинаковым непустым `historyId` объединяются, последняя попытка выбирается по `stop`, затем `start`, затем порядку файла. Без `historyId` каждый результат считается самостоятельным. Число попыток отображается отдельно.
- Длительность теста — `(stop − start) / 1000` секунд при наличии обеих отметок и `stop >= start`. Иначе длительность отсутствует и не участвует в статистике времени.
- P95 рассчитывается в PostgreSQL как `percentile_cont(0.95)` по отдельным корректным длительностям итоговых тестов за выбранный период и фильтры. Это интерполированный перцентиль выборки; при отсутствии наблюдений значение не показывается. Доступные сейчас в VictoriaMetrics сумма и число измерений не позволяют получить P95.
- Исход прогона определяется по итогам тестов в порядке приоритета: `broken`, `failed`, `unknown`, `skipped`, `passed`. При отсутствии результатов — `unknown`. Статус обработки импорта отображается отдельно от исхода тестов.
- Значения на панелях зависят от общего фильтра времени и выбранных проектов. Фильтр набора применяется к тестовым панелям; общий исход прогона определяется по всем его тестам и от выбора набора не меняется, что указано в названии панели.

## Предлагаемые панели

| № | Панель и формат | Что фактически отображается | Источник |
| --- | --- | --- | --- |
| 1 | **Сводка прогонов**, таблица | Проект, номер и ссылка сборки, время приёма, итоговый статус тестов, статус импорта, количество итоговых тестов и попыток | PostgreSQL, представления импортов и итоговых тестов |
| 2 | **Исходы прогонов**, столбцы по времени | Число завершённых прогонов по `passed`, `failed`, `broken`, `skipped`, `unknown` для выбранных проектов | PostgreSQL, исходы импортов |
| 3 | **Итоги тестов**, карточки и график | Число итоговых тестов по статусам и доля `passed` от всех итогов; отдельно число попыток | PostgreSQL, итоговые результаты и попытки |
| 4 | **Медленные тесты**, график | Топ-10 идентичностей тестов по максимальной длительности за период; каждая серия — фактические значения длительности теста по прогонам. Легенда: название теста и проект; при совпадении имён добавить отличающий идентификатор | PostgreSQL, длительности итоговых тестов |
| 5 | **Топ тестов по длительности**, таблица | Для тех же тестов: проект, название, число измерений, средняя длительность, P95 и максимум; сортировка по максимуму | PostgreSQL, отдельные длительности тестов |
| 6 | **Распределение времени тестов**, график | P50, P95 и максимум длительности итоговых тестов по временным интервалам для выбранных проектов и наборов | PostgreSQL, `percentile_cont` и `max` по отдельным длительностям |
| 7 | **Самые долгие прогоны**, таблица | Проект, сборка, время приёма, статус и длительность окна тестов: от минимального корректного `start` до максимального `stop` в импорте. Это не время Jenkins job | PostgreSQL, результаты тестов |
| 8 | **Очередь и обработка**, график | Текущее число заданий очереди по состояниям и время обработки импортов; показатели всей платформы, без фильтра проекта | VictoriaMetrics, существующие агрегаты |

Для топа тест определяется по `historyId` внутри проекта; при его отсутствии результат не объединяется с другими по одному имени. Если тесты имеют одинаковое отображаемое название, легенда дополняется `fullName` или коротким идентификатором. Серии Grafana строятся из SQL-результата для ограниченного топа; они не создают постоянные ряды с именами тестов в VictoriaMetrics.

## Проверка перед приёмкой

Проверить два разных Jenkins `JOB_NAME`, выбор каждого проекта и группы «Неизвестный проект», разделение результатов и стабильный повтор одной сборки. Для известной выборки с повторами, одинаковыми названиями тестов, пропущенными и неверными интервалами сверить таблицы, топ, итоговые статусы и P95 с независимым расчётом. Отдельно проверить ограничения прав пользователя Grafana, фактические SQL-запросы и видимые легенды в браузере. Существующие записи, не содержавшие метаданных, сохранить без изменения.
