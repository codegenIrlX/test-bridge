# Дальнейшее развитие TestBridge: аналитика прогонов Allure

## Цель и границы

Следующий приоритет — общая аналитика прогонов: количество и результаты тестов, длительность и тренды по проектам и наборам. PostgreSQL остаётся хранилищем деталей, а агрегированные метрики передаются через OpenTelemetry Collector в VictoriaMetrics для отображения в Grafana.

Критерии приёмки: данные прогонов и статусы сохраняются без потери существующей информации; повторная обработка не удваивает метрики; цепочка доставки и дашборд проверены на реальном прогоне Jenkins.

Ниже приведено состояние по текущим исходникам проекта и анализу предоставленного ZIP. В примере 9 исходных файлов результатов; все имеют статус `passed`, поэтому ошибки и повторы по нему проверить нельзя.

## Что уже хранится

### Таблица `imports` — обработка архива

| Поле | Назначение | Источник |
| --- | --- | --- |
| `id` | Идентификатор импорта | Генерируется платформой |
| `status` | `pending`, `processing`, `completed` или `failed` | Состояние обработки платформой |
| `error_message` | Безопасное описание ошибки импорта | Платформа |
| `attempt_count` | Количество попыток обработки | Платформа |
| `archive_deleted` | Признак удаления архива после обработки | Платформа |
| `created_at` | Время регистрации импорта | PostgreSQL |

`imports.status` обозначает результат обработки архива, а не результат тестов.

### Таблица `test_results` — тесты

| Поле | Назначение | Источник |
| --- | --- | --- |
| `id` | Внутренний идентификатор результата | Генерируется платформой |
| `import_id` | Связь результата с импортом | Платформа |
| `position` | Порядок файла результата в архиве | Платформа |
| `name` | Название теста | Allure `name` |
| `started_at_ms` | Начало выполнения, миллисекунды Unix | Allure `start` |
| `stopped_at_ms` | Окончание выполнения, миллисекунды Unix | Allure `stop` |

Длительность можно вычислить как `stop − start`, если оба значения присутствуют и корректны. Отдельное поле длительности сейчас не сохраняется.

### Таблица `test_steps` — шаги тестов

| Поле | Назначение | Источник |
| --- | --- | --- |
| `id` | Внутренний идентификатор шага | Генерируется платформой |
| `test_id` | Тест, которому принадлежит шаг | Платформа |
| `parent_id` | Родительский шаг; `NULL` для корневого | Вложенность Allure `steps` |
| `position` | Порядок среди соседних шагов | Порядок в Allure `steps` |
| `name` | Название шага | Allure `steps[].name` |
| `started_at_ms` | Начало шага, миллисекунды Unix | Allure `steps[].start` |
| `stopped_at_ms` | Окончание шага, миллисекунды Unix | Allure `steps[].stop` |

Парсер читает исходные `*-result.json`, включая вложенные шаги. Статусы тестов и шагов, идентификаторы Allure, метки, фикстуры и вложения в БД не сохраняются. Источники: [схема БД](../../../metrics_srv/schema.sql), [парсер](../../../metrics_srv/parser.py).

## Что ещё можно разбирать

| Данные Allure или CI | Есть в примере | Что дадут для аналитики | Приоритет |
| --- | --- | --- | --- |
| Статус теста `status` | Да, только `passed` | Количество и доля `passed`, `failed`, `broken`, `skipped`, `unknown` | Высокий |
| Статус шага `steps[].status` | Да | Количество неуспешных шагов и распределение их длительности | Высокий |
| Идентификаторы `uuid`, `historyId`, `testCaseId`, `fullName` | Да | Сопоставление тестов между прогонами, история и основа для анализа нестабильности | Высокий |
| Метки `suite`, `parentSuite`, `subSuite`, `tag` | Да | Агрегация по наборам и согласованным категориям | Высокий |
| Метки `framework`, `language` | Да | Сравнение агрегатов по стеку тестов | Средний |
| Проект, job, номер сборки, ссылка и ревизия | Требуют отдельного источника CI | Привязка импорта к проекту и конкретному прогону Jenkins | Высокий |
| Параметры теста `parameters` | В проверенных результатах не обнаружены | Различение параметризованных случаев при анализе истории | Средний |
| Причина ошибки `statusDetails` | В примере успешных тестов не подтверждена | Классификация ошибок и диагностика падений | Средний |
| Фикстуры из `*-container.json` | Контейнеры есть; первый этап их пропускает | Время подготовки и очистки, ошибки фикстур | Позже |
| Вложения `attachments` | Да | Доступ к материалам диагностики | Позже; для агрегированных метрик не требуется |

Наличие поля зависит от адаптера Allure и конкретного прогона. Форматы описаны в документации [Allure result file](https://allurereport.org/docs/how-it-works-test-result-file/) и [container file](https://allurereport.org/docs/how-it-works-container-file/).

## Этапы развития

- [ ] **Architect:** определить контракт прогона, идентификацию проекта, минимальные метаданные Jenkins и правила миграции; допустимые файлы — `docs/` и `docs/diagrams/`; зависимость — согласование требований; проверка — совместимость существующего API и данных.
- [ ] **Developer:** добавить через миграции статусы тестов и шагов, идентификаторы Allure, выбранные метки и связь с прогоном; допустимые файлы — приложение, миграции и документация контрактов; зависимость — контракт прогона; проверка — сохранность существующих данных и проверка API/OpenAPI.
- [ ] **Architect:** определить правила агрегации повторных попыток, отсутствующих значений, неполных и повторно отправленных архивов; допустимые файлы — архитектурная документация; зависимость — контракт данных; проверка — различимость показателей попыток тестов и итогов прогонов.
- [ ] **Developer:** подготовить агрегаты по числу тестов и статусов, длительности, результатам импортов, времени обработки и состоянию очереди; допустимые файлы — приложение и связанная документация; зависимость — правила агрегации; проверка — повторная обработка без двойного учёта.
- [ ] **Developer:** реализовать экспорт метрик, подключить OpenTelemetry Collector и VictoriaMetrics; допустимые файлы — приложение и эксплуатационная конфигурация; зависимость — агрегаты; проверка — доставка после перезапусков и повторной обработки.
- [ ] **Developer:** создать первый дашборд Grafana: прогоны и тесты по статусам, доля успешных тестов, длительность и динамика; допустимые файлы — конфигурация Grafana и связанная документация; зависимость — доступные метрики; проверка — данные реального прогона Jenkins.
- [ ] **Tester:** добавить архивы со статусами `failed`, `broken`, `skipped`, вложенными шагами, повторами, параметрами и отсутствующими необязательными полями; допустимые файлы — `tests/`; зависимости — соответствующие этапы реализации; проверка — миграции, повторный импорт, связи и интеграционная цепочка.
- [ ] **Reviewer:** независимо проверить итоговые изменения на чтение; зависимости — реализация и проверки; результат — замечания с доказательствами и оставшиеся риски.

Для метрик не использовать имена тестов, UUID, номера сборок и другие неограниченные значения как метки: это создаёт слишком много временных рядов. См. [Prometheus instrumentation](https://prometheus.io/docs/practices/instrumentation/). Детализацию отдельных тестов и шагов оставить в PostgreSQL для следующего этапа.

После накопления истории можно добавить анализ нестабильных тестов, повторов, фикстур и классификацию ошибок. Вложения рассматривать отдельно от метрик.

## Ограничения

Уже обработанные архивы удалены. Поля, которые ранее не сохранялись, нельзя восстановить из текущей БД; для их заполнения потребуется повторно получить исходные результаты из CI или другого хранилища.

Это план развития; миграции, метрики и Grafana пока не реализованы.
