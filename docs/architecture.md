# Архитектура обработки Allure

Схема показывает, как Jenkins передаёт архив, а TestBridge обрабатывает его и сохраняет результат. [Схема обработки Allure](diagrams/allure-import.drawio)

## Назначение и границы

TestBridge принимает ZIP с исходными результатами Allure из CI, разбирает тесты и сохраняет данные для последующего анализа. Первый этап охватывает названия тестов, вложенные шаги и время. Фикстуры, вложения и уже сформированный `allure-report` не разбираются. Метрики, OpenTelemetry Collector, VictoriaMetrics и Grafana остаются за границей этапа.

Приложенный к задаче архив содержит девять исходных файлов `*-result.json` и сформированный отчёт. Источник тестовых данных — файлы результатов; содержимое файлов контейнеров и вложений не переносится в БД.

Архитектура разделяет API, Scheduler и Processor на отдельные процессы. Этот принцип заимствован из [Remnawave](https://github.com/remnawave/backend/blob/6853666801d6d1925b6aec55824106100485777a/ecosystem.config.js); маршруты, модель хранения и жизненный цикл импорта определяются требованиями TestBridge.

## Компоненты и данные

| Компонент | Ответственность |
| --- | --- |
| Jenkins | Отправляет архив на API и получает подтверждение приёма, не дожидаясь обработки. |
| API FastAPI | Проверяет запрос и доступ, сохраняет архив на диск, регистрирует импорт в PostgreSQL, возвращает его идентификатор и состояние. Предоставляет Swagger UI и OpenAPI. |
| Scheduler | Находит задания импорта в PostgreSQL, публикует задачи в BullMQ, восстанавливает постановку после сбоев очереди и удаляет архивы завершённых импортов. |
| BullMQ и Redis | Передают задачу между Scheduler и Processor. Очередь не является единственным источником состояния импорта. |
| Processor | Читает файлы результатов из ZIP, разбирает вложенные шаги и сохраняет результат в PostgreSQL. |
| Мигратор Alembic | Выполняет ревизии схемы PostgreSQL до запуска API, Scheduler и Processor. |
| PostgreSQL | Хранит состояние импорта, результаты тестов и дерево шагов. |
| Общий постоянный диск | Хранит принятые архивы, пока их обработка не завершена и удаление не выполнено. API, Scheduler и Processor видят один и тот же каталог. |

У теста и шага сохраняются название, порядок и время начала и окончания, если оно есть в исходных данных. Шаги сохраняют вложенность. Отсутствующее время не заменяется нулём. Другие поля исходного Allure на первом этапе не являются обязательной частью модели.

## Структура приложения

| Пакет или модуль | Ответственность |
| --- | --- |
| `metrics_srv.__main__`, `metrics_srv.api` | Собирают зависимости для четырёх ролей. Фабрика FastAPI подключает HTTP-маршруты и общие обработчики ошибок. |
| `metrics_srv.domains.imports` | Содержит маршруты и DTO, сценарии приёма, обработки и очистки, парсер Allure, файловый адаптер, репозиторий и ORM-модели. |
| `metrics_srv.db` | Создаёт Engine и фабрику сессий, задаёт общую базу моделей с соглашением об именах и предоставляет mixin для UUID-первичного ключа. |
| `metrics_srv.workers` | Запускает Scheduler и Processor, управляет очередью BullMQ и завершением фоновых процессов. |
| `metrics_srv.migrations` | Содержит окружение, шаблон и ревизии Alembic. Окружение получает метаданные общей базы после регистрации моделей импорта. |

HTTP-маршруты и воркеры вызывают сценарии домена. Сценарии передают открытую сессию репозиторию, управляют фиксацией и откатом, обращаются к парсеру и файловому адаптеру. Репозиторий выполняет запросы и сохраняет результаты через SQLAlchemy. Воркеры выполняют синхронные операции с БД и файлами через `asyncio.to_thread`.

## Приём и обработка

1. Jenkins отправляет ZIP в `POST /api/v1/imports` как `multipart/form-data` с полем `file` и сервисным токеном.
2. Сценарий приёма полностью записывает архив на постоянный диск, затем регистрирует импорт в PostgreSQL. Только после этого API возвращает `202 Accepted` с идентификатором. При повторной загрузке с тем же `Idempotency-Key` и тем же содержимым API возвращает существующий импорт. Если содержимое изменилось, API возвращает `409`.
3. Scheduler обнаруживает задание и публикует его в BullMQ. Состояние в PostgreSQL позволяет восстановить постановку, если Redis или Scheduler были недоступны.
4. Processor удерживает advisory lock на одном физическом соединении с `NullPool`. Он фиксирует начало попытки отдельной транзакцией, затем читает `*-result.json` вне транзакции. Результаты тестов, вложенные шаги и статус `completed` записываются атомарно.
5. Scheduler запускает очистку независимо от Redis. Сценарий выбирает завершённые импорты через `FOR UPDATE SKIP LOCKED` и удаляет их архивы после фиксации результатов. Если удаление не удалось, следующая попытка откладывается на пять минут.
6. `GET /api/v1/imports/{import_id}` позволяет узнать состояние импорта. При неуспешном разборе клиент получает безопасное описание ошибки; исходный архив остаётся для диагностики и повторного запуска.
7. `POST /api/v1/imports/{import_id}/retry` возвращает неуспешный импорт в состояние `pending`, если архив сохранился. Метод возвращает `202`, и Scheduler снова ставит импорт в очередь. Для отсутствующего импорта API возвращает `404`, а если повтор невозможен — `409`.

Импорт проходит состояния `pending`, `processing`, `completed` или `failed`. `completed` означает фиксацию результатов в PostgreSQL. Факт удаления архива хранится отдельно в `archive_deleted`, поэтому сбой очистки не меняет результат разбора. Путь к архиву определяется UUID импорта.

Запись файла и запись в PostgreSQL не образуют общей транзакции. Реализация должна учитывать остановку между этими операциями и не подтверждать приём до сохранения задания. Аналогично очередь и PostgreSQL не образуют общей транзакции: восстановление должно исключать потерю принятых заданий и дубли результатов. На объём ZIP и его содержимого действуют настраиваемые ограничения.

## HTTP и документация

Все методы платформы, включая реализованные служебные методы, представлены в Swagger UI. OpenAPI формируется FastAPI из фактических маршрутов и моделей: он содержит параметры, форматы запросов, авторизацию, успешные ответы и ошибки. Swagger позволяет передать сервисный токен и загрузить ZIP.

Ошибки HTTP возвращаются в объекте `error` с полями `code`, `message` и `details`. Секреты, содержимое архивов и внутренние детали ошибок не передаются клиенту. Доступ к Swagger сам по себе не заменяет проверку токена защищёнными методами API.

## Конфигурация и размещение

Настройки приложения находятся в `config.yaml`, секреты — в `secrets.yaml`. `METRICS_SRV_ENV` выбирает окружение, по умолчанию используется `development`; общие настройки и настройки окружения загружаются и проверяются через `metrics_srv.config`. Конфигурация поставляется с примерами без действующих секретов. Файл `secrets.yaml` исключён из Git и контекста сборки.

Docker Compose запускает API, Scheduler, Processor, мигратор, PostgreSQL и Redis. Команды всех четырёх ролей приложения используют общий образ. Постоянные тома сохраняют данные PostgreSQL, очередь Redis и принятые архивы при пересоздании контейнеров. Конфигурационные файлы передаются при запуске, файл секретов доступен необходимым сервисам через Compose secrets. PostgreSQL получает пароль для инициализации из секрета через временный файл.

Одноразовый сервис `migrate` ждёт готовности PostgreSQL и выполняет `upgrade head`. API, Scheduler и Processor ждут готовности Redis и успешного завершения мигратора. Порт API опубликован на хосте, PostgreSQL доступен с хоста по `127.0.0.1:5433`, Redis доступен внутри сети Compose. Первая ревизия рассчитана на чистую PostgreSQL 17. ## Проверка

Проверка должна охватывать отправку предоставленного ZIP и сохранение девяти результатов с вложенными шагами, подтверждение `202`, запрос состояния, удаление файла после транзакции, повтор задания без дублей и восстановление при отказах очереди и БД. Отдельно проверяются повреждённый архив, отсутствие результатов, неверный JSON, ошибки очистки и ограничения архива.

Для API сверяются реальные запросы и ответы с OpenAPI и работой Swagger UI. Для конфигурации проверяются выбор окружения, валидация и отсутствие секретов в логах и образе. Для Compose отдельно подтверждаются конфигурация, сборка, запуск, миграции, обработка импорта и сохранность томов после пересоздания; успешная статическая проверка Compose не подтверждает запуск системы.
