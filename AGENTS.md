# TestBridge

## Проект и проверки

- **Назначение:** TestBridge Metrics Service — приём ZIP-архивов с исходными результатами Allure из Jenkins, их разбор и хранение в PostgreSQL для последующего анализа.
- **Стек:** Python 3.12+, FastAPI, uvicorn, SQLAlchemy 2.x, Alembic, psycopg 3, BullMQ, PyYAML,
  PostgreSQL 17, Redis 7.
- **Процессы:** `api` (FastAPI/uvicorn на порту 8000), `scheduler` (asyncio), `processor` (asyncio), `migrate` (подготовка схемы PostgreSQL). Все роли запускаются из одного образа: `python -m metrics_srv <роль>`.
- **Очередь:** BullMQ через Redis, имя очереди — `ALLURE_IMPORTS_QUEUE`.
- **Проверки кода:** `ruff check .` (строка 100 символов, target `py312`).
- **Тесты:** локальные unit-тесты запускай через `pytest`. Интеграционные проверки проводи на рабочем стенде.
- **Запуск платформы:** `docker compose up -d --build` поднимает весь TestBridge из `compose.yaml`, включая аналитику.

## Порядок работы

- Изучи применимые инструкции и связанные файлы. Проверь `git status` и сохраняй пользовательские изменения
  в рабочей копии и индексе.
- При неопределённом объёме согласуй план до правок. Сообщай о результатах и ограничениях проверок,
  несовместимых изменениях и миграциях. Указывай причины пропуска проверок.
- Защищай секреты и персональные данные, в том числе в примерах, логах и ответах клиенту.
- Для разработки и интеграционных проверок используй рабочие БД и Redis проекта `testbridge` и существующий Jenkins.
  Не создавай отдельные БД, Jenkins или Compose-проекты для разработки и проверок. Сохраняй рабочие данные.
- При правках этого `AGENTS.md` соблюдай лимит в 200 строк, включая пустые.

## Планирование и работа агентов

- Координатор выполняет роль `tech-lead`. Для каждой задачи по репозиторию, включая анализ без правок
  кода, создай один файл `docs/plan/<задача>/<slug>.md` до выполнения. До его записи допустимы чтение инструкций,
  проверка Git и сбор фактов для плана. При уточнении задачи обновляй тот же файл. Если текущий режим
  запрещает запись, покажи план в чате и укажи, что сохранить его не удалось.
- Укажи цель, границы и критерии приёмки. Разбей работу на пункты `- [ ]`. Для каждого укажи роль,
  ожидаемый результат, допустимые файлы, зависимости и проверку. Для простой задачи достаточно краткого плана.
- Выбирай из [профилей агентов](.opencode/agents/) только нужные роли. Передай агенту путь к плану, входные файлы,
  границы поручения и формат результата. При запуске указывай тип профиля по его имени, если интерфейс
  это поддерживает. Иначе передай те же правила в поручении и укажи, какой профиль не удалось запустить.
  Назначай одного владельца на файл. Если меняется объём работ, обнови план до передачи новых поручений.
  Запускай независимые шаги
  параллельно, когда они могут работать без результатов друг друга и не редактируют один файл.
- Только `tech-lead` ведёт файл плана. `analyst` формулирует требования на чтении. `architect` пишет
  назначенные архитектурные документы в `docs/` и схемы в `docs/diagrams/`. `developer` правит назначенные файлы
  приложения, миграций, эксплуатации и связанной документации. `tester` правит назначенные файлы в `tests/`.
  `reviewer` независимо проверяет результат на чтении. Специалисты возвращают результат координатору.
  Изменения `AGENTS.md` и профилей ведёт основная сессия по прямому поручению пользователя.
- Для чтения используй просмотр файлов и поиск по репозиторию. В поручениях профилям Git доступен для просмотра
  состояния и diff без внешних обработчиков (`git --no-optional-locks status --short`,
  `git diff --no-ext-diff --no-textconv`, `git diff --cached --no-ext-diff --no-textconv`).
  Для локальных проверок `developer` и `tester` используют команды
  Ruff и pytest из раздела «Проект и проверки» с активным Python проекта. Для базового прогона pytest выбирай
  относящиеся к шагу тесты. БД, Docker и Jenkins проверяет основная сессия на рабочем стенде. Операции Git
  на запись, действия в Jenkins и произвольные команды выходят за рамки поручений профилей.
- Пути и команды задают границы поручения. OpenCode наследует песочницу и согласования основной сессии.
  Если ревью требует технического запрета записи, запускай его в отдельном сеансе `read-only`.
- Получив результат, `tech-lead` сверяет его с критериями и проверками, возвращает дефекты владельцу
  и закрывает чекбоксы по подтверждённым результатам. Для оставшихся шагов фиксирует причину и следующий шаг.

## Git и README

- Новые рабочие ветки именуй в формате `<тип>/<название>`. Тип выбирай по задаче: `feat`, `fix`, `chore`,
  `docs`, `test`, `refactor` или другой осмысленный тип. Название пиши строчными латинскими буквами,
  цифрами и дефисами, например `feat/import-reliability` или `fix/archive-cleanup`.
  По умолчанию основание новой ветки — локальная `dev`. Явно указанное основание имеет приоритет.
- При работе с ветками и коммитами используй [commit](.agents/skills/commit/SKILL.md).
  Перед коммитом согласуй точный заголовок и состав изменений.
  Если они уже явно согласованы и остались прежними, переходи к коммиту. При изменении заголовка или состава
  согласуй обновлённый вариант. Для push, PR, merge, release и размещения нужно отдельное поручение пользователя.
- Создавай и изменяй README только по прямому запросу пользователя. Используй [readme](.agents/skills/readme/SKILL.md),
  покажи полный итоговый текст и дождись его согласования до записи. Если README устарел в рамках другой задачи,
  сообщи об этом пользователю.

## Python, docstring и комментарии

- При разработке и ревью Python используй [python-code-style](.agents/skills/python-code-style/SKILL.md).
- Перед проектированием или расширением структуры прочитай
  [руководство по архитектуре](.agents/skills/python-code-style/references/architecture.md).
  Выбирай масштаб по задаче, сохраняй структуру каталогов и избегай пустых слоёв. Сложные компоненты дели
  на подкомпоненты по ответственности.
- Аннотируй публичные интерфейсы и границы данных с учётом версии Python и конфигурации проверок.
- Обрабатывай ожидаемые ошибки явно. Не скрывай сбои широкими `except`. Сообщай об успехе только после
  успешного завершения операции.
- Выбирай sync или async по фактическому стеку. В асинхронном коде учитывай блокирующие вызовы, отмену
  и жизненный цикл ресурсов.
- При написании и редактировании docstring, описаний и комментариев используй
  [human-writing](.agents/skills/human-writing/SKILL.md). Это относится и к описаниям полей DTO и колонок БД.
- Пиши краткие docstring по фактическому назначению. Для Python смотри
  [примеры docstring](.agents/skills/python-code-style/references/docstrings.md).
  В комментариях объясняй причины решений и неочевидные вычисления. Обновляй комментарии вместе с кодом.

## HTTP API и DTO

- При изменении API-контракта прочитай [руководство по DTO](.agents/skills/python-code-style/references/dto.md)
  и используй [sync-backend-openapi](.agents/skills/sync-backend-openapi/SKILL.md) для сверки OpenAPI.
- Размещай DTO в домене-владельце, по одному классу в файле. У каждого DTO, включая наследников и технические
  классы, должен быть собственный краткий docstring на русском. Каждое поле Pydantic DTO описывай через
  `Field(description=...)` с сохранением ограничений валидации.
- В FastAPI используй `camelCase` для именованных полей JSON-запросов и ответов, `snake_case` для атрибутов
  Python и полей БД. Настраивай aliases и проверяй фактический JSON, OpenAPI и совместимость контрактов.
- Проверяй входные данные, права, ответы и ошибки API. Документируй фактические контракты и сверяй изменения
  с потребителями. Не меняй опубликованный контракт без уведомления потребителей. Повышай версию API
  только с явного разрешения пользователя.
- Для всех HTTP API возвращай ошибки в объекте `error` с полями `code`, `message`, `details`. Централизуй
  на транспортной границе преобразование доменных, HTTP-, валидационных и непредвиденных ошибок. Сохраняй
  HTTP-статусы и необходимые заголовки. Скрывай внутренние детали от клиента и логируй непредвиденные ошибки.
- Согласуй переход существующего API на единый формат ошибок с потребителями и обнови OpenAPI. Учитывай
  особенности других протоколов и ограничения обработки ошибок после отправки ответа.

## Конфигурация и БД

- Имена очередей BullMQ записывай в верхнем регистре через подчёркивания с суффиксом `_QUEUE`, например `ALLURE_IMPORTS_QUEUE`.
- Читай переменные окружения через `metrics_srv.config` и проверяй обязательные настройки. Проект использует
  `config.yaml` и `secrets.yaml`; окружение выбирается переменной `METRICS_SRV_ENV` (по умолчанию `development`).
  Когда описываешь запуск, сверяй фактическую загрузку `config.yaml`/`secrets.yaml` с кодом и
  [документацией конфигурации](docs/configuration.md).
- При работе со схемой, SQLAlchemy, транзакциями и миграциями используй
  [database-work](.agents/skills/database-work/SKILL.md).
- Используй общий `DeclarativeBase` с `MetaData.naming_convention` и передавай метаданные со всеми
  зарегистрированными моделями в `target_metadata` Alembic. Форматы имён: `pk__<table>`,
  `fk__<table>__<columns>__<referenced_table>`, `uq__<table>__<columns>`, `ck__<table>__<purpose>`,
  `ix__<table>__<columns>`. Сохраняй порядок колонок и задавай смысловое имя для `CHECK`.
- Используй общий UUID-mixin для первичных ключей импорта, результата и шага. Выноси другие поля
  в mixins при совпадении смысла, типа, ограничений и правил заполнения. Серверные значения задавай в схеме.
- Запускай `python -m metrics_srv migrate` отдельным одноразовым сервисом. В Compose он ждёт
  `service_healthy` PostgreSQL. API, Scheduler и Processor ждут `service_completed_successfully` мигратора.
- Храни ревизии Alembic самодостаточными. Проверяй автогенерацию вручную. На рабочей PostgreSQL сверяй
  применённую ревизию и схему. Не используй откат рабочих миграций для проверки обратимости.
- При работе с БД, транзакциями и миграциями сохраняй проверки доступа и данные средствами проекта.
- Для каждой таблицы и колонки БД обеспечь непустое осмысленное описание. Если СУБД поддерживает
  комментарии, храни описание в схеме. Иначе внеси его в принятую документацию схемы и укажи ограничение.
- Меняй описания в схеме через миграции проекта. Применённые миграции редактируй только по принятому в проекте порядку.

## Тесты и схемы

  проверяй поведение и ошибки. В интеграционных тестах изменяй только данные, созданные самими тестами,
  и освобождай их ресурсы при сбое подготовки.
- Храни схемы в `docs/diagrams/`, sequence-схемы — в `docs/diagrams/sequence/`. Из документов ссылайся на исходники
  sequence-схем.
- Поясняющие заметки, примечания и текстовые выводы добавляй на схемы только по прямому запросу пользователя.
  Названия участников, подписи связей и действий и запрошенная легенда остаются частью схемы.
