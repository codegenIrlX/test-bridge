# ООП в Python

Выбирай объектную модель по поведению, состоянию и точкам изменения. Эти рекомендации относятся к библиотекам, приложениям и тестовым фреймворкам; они не требуют вводить классы или паттерны во всякую задачу. До изменения выясни публичные вызовы, допустимые состояния, ошибки, владельца ресурсов и поддерживаемую версию Python.

## Функция, данные или объект с поведением

| Задача | Подход |
| --- | --- |
| Преобразование без собственного состояния и жизненного цикла | Функция; класс с одними staticmethod обычно не добавляет ответственности. |
| Связанные внутренние данные | Обычная структура или dataclass по нужным операциям; неизменяемость и сравнение выбирай по смыслу. |
| Внешний контракт с валидацией и сериализацией | Принятая модель DTO; следуй [правилам DTO](dto.md), не превращай её в HTTP-клиент. |
| Состояние с инвариантами или собственный ресурс | Класс с явными операциями, жизненным циклом и правилами изменения состояния. |
| Несколько реализаций одной необходимой границы | Узкий контракт потребителя и подходящие адаптеры; общий предок требуется не всегда. |

Разделяй обязанности, когда они меняются независимо: например, HTTP-транспорт, предметная операция и проверка результата теста. Не создавай `BaseClient`, repository, фабрику или service locator только ради названия паттерна. Существующее разумное объединение небольших обязанностей не требует дробления.

## Композиция и подстановка

- Для изменяемой политики или внешней зависимости сначала оцени композицию: передавай транспорт, часы или стратегию явно через конструктор либо аргумент операции. Собирай связанные объекты на принятой границе запуска или в fixtures; DI-контейнер для этого не обязателен.
- Наследование подходит, когда наследник сохраняет поведение, обещанное потребителям базового типа. Проверь допустимые входы, результаты, исключения, побочные эффекты и владение ресурсами. Не усиливай предусловия и не ослабляй гарантии; ошибка вместо согласованного `None`, скрытый повтор POST или закрытие чужой сессии могут нарушить контракт при неизменной сигнатуре.
- Не наследуй клиент от транспорта только ради доступа к его методам; не наследуй тест от крупного базового теста только ради данных и fixtures. Если действующая иерархия нужна фреймворку, сохраняй её контракты и меняй только согласованный участок.
- При добавлении варианта отделяй реально меняющуюся часть. Strategy может быть простой функцией, Adapter — небольшим объектом, фабрика — функцией создания. Дублирование строк само по себе не доказывает единую абстракцию.

## Контракты и типизация

- Конкретный тип достаточен, если потребителю не нужна независимость от реализации. Используй `Protocol` для структурной границы, которой должны удовлетворять независимые объекты; наследовать их от протокола не обязательно. Описывай только требуемые потребителю операции.
- `ABC` уместен для осознанного семейства наследников с общим поведением и обязательными абстрактными операциями. Не добавляй ABC параллельно Protocol без разных задач. Регистрация виртуального подкласса не передаёт реализации методов ABC.
- Аннотации и `@runtime_checkable` не проверяют поведенческий контракт. Runtime-проверка протокола проверяет наличие атрибутов, а не их типы или сигнатуры. Внешние данные валидируй на принятой границе; взаимозаменяемость подтверждай общими сценариями, а не одним `isinstance`.
- Generics нужны, когда сохраняют связь типов входа и результата; не заменяй ими конкретный понятный контракт. Для интерфейса только чтения оцени подходящую абстракцию коллекции, не обещай возможность изменения. Согласованность типов проверь существующим type checker, если он подключён.
- `Self` используй, когда результат действительно сохраняет тип текущего объекта или наследника; метод, всегда возвращающий конкретный базовый класс, не должен обещать `Self`. `@override` помогает проверять намерение переопределения через type checker, но не обеспечивает совместимость поведения во время выполнения. Синтаксис generics и доступность этих средств выбирай по версии проекта, не добавляй backport или обновление Python ради примера.

## Состояние, инварианты и жизненный цикл

- После создания объект должен находиться в согласованном состоянии. Изменяй связанные поля одной операцией, предварительно проверив новые данные; частичная ошибка не должна оставлять смесь старого и нового состояния. Публичный setter оправдан реальной операцией, а не желанием открыть каждое поле.
- Не храни изменяемый контекст запроса или теста в атрибуте класса. Для каждого экземпляра создавай собственные коллекции, у dataclass используй подходящий `default_factory`. При передаче mutable объекта реши, кто им владеет: ссылка, копия или неизменяемое представление должны соответствовать контракту.
- Property сохраняет удобство чтения атрибута; не прячь в ней неожиданный сетевой вызов, обновление токена или изменение внешних данных. Если существующий интерфейс уже имеет такие эффекты, не меняй их молча: обозначь совместимость и предложи явную операцию.
- Различай полученный извне и созданный внутри ресурс. Закрывает его согласованный владелец; injected transport или сессия не становятся собственностью клиента автоматически. При собственном ресурсе обеспечь освобождение после успеха, ошибки и частичного setup; используй контекстный менеджер или принятый lifecycle. Не полагайся на `__del__` для своевременного закрытия.
- Для объекта с состояниями «открыт/закрыт» или «активен/завершён» определи допустимые повторные вызовы и ошибку использования. Конкурентное использование разрешай только при предусмотренной синхронизации; локальный lock не координирует отдельные процессы.

## Модель данных Python

- У dataclass `frozen=True` ограничивает присваивание полей, но не замораживает вложенный list или dict. Для value object при необходимости нормализуй вход в неизменяемые компоненты и проверь независимость от исходной коллекции. `slots=True` не обеспечивает неизменяемость; оцени совместимость с наследованием, сериализацией и используемой библиотекой до его добавления.
- Выбери равенство по значению или по идентичности объекта. Равные hashable объекты должны иметь одинаковый hash, а поля, влияющие на hash ключа, не должны меняться, пока он используется в dict/set. Не включай `unsafe_hash=True` как обход ошибки без анализа этого контракта.
- Представление объекта должно быть безопасным: исключай секреты из dataclass repr через `field(repr=False)` или принятый механизм. Это не защищает сериализацию, логи и отчётные вложения автоматически; проверь соответствующие пути отдельно.
- При множественном наследовании `super()` продолжает поиск по MRO, а не просто вызывает «родителя». Для кооперативной цепочки согласуй сигнатуры и вызовы `super()`; mixin должен иметь узкую роль и явные требования к объекту. Не добавляй mixin с неявным общим mutable состоянием.
- Дескрипторы, метаклассы и динамические `__getattr__`/`__getattribute__` применяй при конкретной потребности существующего API. До добавления оцени обычную композицию, property или явный метод; проверь ошибки доступа, типизацию и наблюдаемые побочные эффекты. Сложность механизма сама по себе не делает архитектуру лучше.

## Проверки по изменённому поведению

Выбери относящиеся к задаче сценарии: одинаковый контракт разных реализаций, отсутствие смешения состояния экземпляров, границы инварианта, отказ без частичного изменения, владение и закрытие ресурса, повторное использование, согласованность equality/hash, безопасность repr. Для адаптера используй независимый fake, когда он помогает проверить границу, но не объявляй такую проверку подтверждением реального HTTP или БД. Для чистой функции без этих рисков достаточно её существующих проверок; тесты на названия классов и количество слоёв не подтверждают поведение.

Примеры возможностей в этих источниках относятся к Python 3.12; для иной версии сверяй её документацию.
