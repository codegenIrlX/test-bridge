# Асинхронные тесты и ресурсы

Применяй при реальном async-коде или конкурентном I/O. Не переводись на async ради скорости небольшого синхронного набора. Сначала установи версию Python, клиент/драйвер, async-плагин pytest и его режим по конфигурации; инструкции `pytest-asyncio` нельзя автоматически переносить на AnyIO.

## Runner, fixtures и event loop

- В `pytest-asyncio` strict-режим требует async-маркер у теста и `@pytest_asyncio.fixture` у async-fixture; auto-режим имеет другие правила. Сохраняй принятый режим и проверь совместимость с другими async-плагинами. [Документация режимов](https://pytest-asyncio.readthedocs.io/en/stable/concepts.html#test-discovery-modes).
- Scope кеширования fixture и срок жизни event loop — разные настройки. Создание, использование и закрытие привязанного к loop клиента должны быть совместимы с ними; не дели session-клиент между несовместимыми loops. Параметры и defaults сверяй с установленной версией плагина.
- В async-тесте используй `await`, не запускай вложенный `asyncio.run()` в уже работающем loop. Runner принадлежит внешней границе выполнения, когда её не предоставляет pytest-плагин.
- `asyncio.Runner`, `TaskGroup` и `asyncio.timeout` доступны с Python 3.11; не предлагай их проекту Python 3.10 без согласованного изменения версии. Для поддерживаемой версии используй доступный механизм запуска и ограничений времени.
- При подмене coroutine используй подходящий `AsyncMock`/fake. Для async context manager настрой также вход и выход контекста; обычный mock возвращаемого значения может не воспроизвести протокол клиента.

## Конкурентность и ошибки

- Выполняй параллельно независимые операции. Зависимые create/update и шаги сценария сохраняют требуемый порядок. Ограничивай одновременно активные запросы и учитывай умножение нагрузки на число workers.
- `Semaphore` ограничивает конкурентность, но не число запросов в секунду. Rate limit требует отдельной политики времени/квоты, если этого требует стенд. `asyncio.Lock` координирует задачи соответствующего loop, а не потоки и процессы.
- Для группы связанных задач определи политику частичного сбоя. `TaskGroup` ожидает завершение группы и при обычной ошибке отменяет оставшиеся задачи. У `gather` распространение первой ошибки само по себе не отменяет остальные задачи; их жизненным циклом всё равно владеет вызывающий код. [Документация задач](https://docs.python.org/3/library/asyncio-task.html).
- При `return_exceptions=True` разбери каждый результат, включая отмену. Отфильтровать неудачи и вернуть только успехи недостаточно для прошедшего теста; допустимость частичного результата задаёт проверяемый контракт.
- Храни ссылки на запущенные фоновые задачи. При завершении сценария останови и дождись принадлежащих ему задач, получи их исключения. Одного `cancel()` недостаточно для подтверждения завершённого cleanup.

## Освобождение и timeout

Создавай клиент/сессию через async-fixture и `async with` либо явный `try/finally`. Прочитай и освободи response согласно API клиента до закрытия его владельца; не возвращай потребителю непрочитанный поток из уже закрытой сессии. Очистка должна охватывать частичный setup до `yield`; если сбой произошёл в `__aenter__`, частично созданные ресурсы освобождает сам механизм входа.

Не поглощай `CancelledError`: выполни допустимый cleanup и передай отмену дальше. Для критичного завершения используй ограниченный по времени механизм, согласованный с библиотекой; shielding не делает бесконечную операцию безопасной. Timeout/отмена клиента не доказывают отмену операции на сервере — учитывай возможный созданный ресурс и идемпотентность.

Если используются очереди, каждому успешно полученному элементу сопоставь `task_done()` в подходящем `finally`. `queue.join()` подтверждает учёт элементов, а не успешность обработки; ошибки workers должны попасть в результат теста. Не добавляй очередь только ради параллельных запросов.

Блокирующий I/O внутри async пути выноси через доступный адаптер, например `to_thread`, когда это обосновано. Это допустимая граница sync/async, а не запрет их сочетать. Отмена ожидающей coroutine обычно не останавливает уже работающую функцию потока: её побочные эффекты и освобождение остаются ответственностью владельца. `to_thread` не является универсальным ускорителем CPU-кода под GIL; способ CPU-параллелизма выбирается отдельно. [Ограничения to_thread](https://docs.python.org/3/library/asyncio-task.html#asyncio.to_thread).

## Что проверять

Для затронутого поведения проверь успех, timeout, ошибку одной задачи, отмену и освобождение уже полученных ресурсов. Используй управляемые события/барьеры для воспроизведения гонки, а не надежду на длительный sleep. Локальный fake подтверждает обработку конкурентности, но не пропускную способность или корректность реального сервиса. Не добавляй нагрузочный прогон в обычный async-тест без отдельной задачи.
