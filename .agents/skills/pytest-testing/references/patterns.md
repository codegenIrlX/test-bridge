# Паттерны тестирования

Выбирай приёмы по проверяемому поведению и фактическим зависимостям проекта. Они применимы к собственному коду фреймворка и к тестам приложения; подмена внешнего API меняет границу подтверждения. Не добавляй Hypothesis, freezegun, mock-плагин или БД только ради примера.

## Сценарии, параметры и ошибки

- Отделяй подготовку, действие и наблюдаемое ожидание. Один тест выражает связное поведение; несколько полей одного результата не требуют отдельных тестов автоматически.
- Параметризуй варианты с одинаковым сценарием и разными значимыми входами/ожиданиями. Явно перечисляй классы эквивалентности и границы; не строй декартово произведение без пользы. Читаемые `ids` не содержат секретов и персональных данных.
- Ожидание следует контракту, а не копии алгоритма под тестом. Проверь, что положительные и отрицательные примеры действительно различаются; простое наличие символов в строке не заменяет согласованную валидацию.
- В `pytest.raises` помещай только действие, которое должно вызвать ожидаемую ошибку. Проверяй конкретный тип и устойчивую часть сообщения/атрибуты; ошибка setup не должна случайно удовлетворить проверку.
- Для ошибочного API-payload не используй успешную DTO-валидацию как непреодолимый входной барьер. Сохрани отдельный путь отправки намеренно неверных данных и проверяй реальный ответ backend.

## Подмены и наблюдаемое поведение

- Подменяй имя там, где код его ищет: при `from module import operation` обычно нужен patch имени в потребляющем модуле. Предпочитай явную передачу зависимости, когда она уже предусмотрена архитектурой.
- `spec`, `spec_set` или `autospec` полезны для контроля интерфейса mock; выбирай по объекту и не считай их доказательством семантики реальной интеграции. Проверяй возвращаемый результат/ошибку, а вызовы — если аргументы, порядок или количество являются частью контракта.
- Не подменяй саму проверяемую бизнес-операцию. Для HTTP-клиента подходящий fake transport может сохранить реальную сериализацию и разбор ответа; такой тест остаётся локальным.
- Через `side_effect` моделируй временный сбой, успех после него и исчерпание попыток, только если retry уже предусмотрен. Проверяй отсутствие повторов постоянной ошибки и изменяющей операции без подтверждённой идемпотентности. Управляй задержкой через принятую зависимость, а не жди реальные секунды.
- Для async используй awaitable-подмену и проверяй ожидание вызова, когда оно существенно; детали — в [async](async.md).

## Окружение, время и данные

- При проверке default явно удаляй соответствующую переменную через `monkeypatch.delenv(..., raising=False)`. Для override задавай её через `monkeypatch.setenv`; не полагайся на окружение машины. Проверяй приоритет источников и отсутствие обязательного значения отдельно.
- Файлы создавай в `tmp_path`/`tmp_path_factory` согласно scope; указывай кодировку текстовых данных. Подмену cwd/путей делай обратимой. Синтаксически правильный путь не доказывает доступность файла.
- В проверках времени управляй часами в месте использования. Различай UTC/часовой пояс и монотонную длительность; проверь момент до, на и после границы. Freeze wall clock не доказывает управление monotonic, event loop или внешним сервером.
- Используй детерминированные входы для проверок конкретного правила. Для генераторов сохраняй воспроизводимый seed по принятому механизму, но не раскрывай сырые данные. Seed одного процесса не гарантирует тот же порядок параллельных событий.
- Не меняй общий объект параметра или fixture между тестами; создавай новое состояние для каждого владельца. Фабрика данных и fixture ресурса имеют разные обязанности.

## Проверки свойств

Property-based testing полезен для инвариантов парсинга, преобразований, генераторов и структур данных. Используй его при наличии инструмента или обоснованной потребности; не вводи обязательный стиль для всех тестов.

Опиши допустимый диапазон входов и независимое свойство: round-trip в пределах контракта, сохранение количества элементов, уникальность или монотонность. Для сохранения коллекции с повторами сравнение `set` недостаточно: нужны, например, счётчики элементов. Самообратимость двух одинаково ошибочных преобразований не заменяет известных примеров.

Один function-scoped fixture может обслуживать много сгенерированных примеров одного теста. Обеспечь изоляцию каждого примера внутри проверки либо используй подходящий механизм инструмента. Для внешних API учитывай множество изменяющих вызовов, ограничения и cleanup; не переносись со свойств чистой функции на живой стенд автоматически. Сохраняй минимальный воспроизводимый контрпример.

## База данных и реальные интеграции

Используй фактическую СУБД и драйвер, когда проверяются её ограничения, транзакции или блокировки. SQLite/fake не подтверждают PostgreSQL-поведение. Session, connection и engine закрываются владельцем и при частичном setup; очистка не сводится к общему autouse-удалению таблиц.

Rollback тестовой транзакции помогает только для операций, реально участвующих в ней. Отдельное соединение backend, собственный commit или внешний HTTP-запрос могут выйти за эту границу. После ожидаемого `IntegrityError` восстанови транзакцию по правилам драйвера/ORM перед дальнейшей работой. Для общей среды используй идентифицируемые собственные данные и разрешённую очистку.

Проект внешних API-тестов не получает доступ к БД другого сервиса автоматически. Проверяй через подтверждённый контракт; дополнительный SQL-oracle применим лишь при согласованном доступе и понимании согласованности данных.
