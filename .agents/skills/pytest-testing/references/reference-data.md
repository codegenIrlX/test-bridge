# Справочники тестовых данных

Тестовый справочник — именованные повторно используемые варианты для сценариев. Источник актуальных записей и их ID — приложение. Enum содержит варианты, нужные тестам, и не объявляет каталог приложения полным или закрытым. Случайные фабричные данные, request/response DTO и полученные во время запуска записи не становятся справочниками автоматически. Эти правила не определяют хранение справочников приложения.

## Структура и значения

- Каждый тестовый справочник оформляй отдельным enum-классом в собственном файле `dictionaries/<name>.py` у владельца тестового домена. Сохраняй принятый корневой пакет, не помещай тестовые enum в backend приложения. Импортируй другие справочники из их модулей; не определяй их в `__init__.py`, явный реэкспорт допустим.
- Имя класса — PascalCase, модуля — snake_case, элементов — UPPER_SNAKE_CASE. Для каждого enum создай один соответствующий файл `test_<name>.py` с нужными проверками; фикстуры и клиенты остаются у своих владельцев.
- Для строковых кодов используй `StrEnum` с явными стабильными значениями. В Python ниже 3.11 применяй совместимый `class Code(str, Enum)` без обновления версии или нарушения существующего контракта. Не используй `auto()`.
- Для записи с несколькими атрибутами используй `Enum` с типизированным неизменяемым значением, например `frozen` dataclass. Не используй изменяемые dict/list или ID конкретного стенда как значения. Python-атрибуты остаются в snake_case, внешние aliases принадлежат API DTO; внутреннее значение enum не является DTO автоматически.
- Исключай неявные aliases и дубли ключей. `@unique` проверяет равенство enum-значений; уникальность стабильного `code` в составных записях проверяй отдельно. При проверках учитывай `__members__`, чтобы aliases не скрывались итерацией. `Enum.name` — техническое имя элемента; доменное название составной записи находится в её значении.
- Существующие проекты приводи к этим правилам в согласованном объёме; не меняй незаметно публичные контракты, импорты или поведение потребителей.

## Значения окружения и получение ID

- Храни стабильный согласованный ключ и нужные метаданные варианта. ID определяй при подготовке или выполнении сценария для текущего окружения через существующий API-клиент либо разрешённый repository/DAO. Не добавляй доступ к закрытой БД другого сервиса ради теста и не вводи новый слой для одного вызова.
- Передавай клиент или repository, окружение и применимые tenant/регион явно через fixtures и принятые сценарные компоненты. Не выполняй HTTP/SQL при импорте, collection, создании enum или чтении атрибутов. Enum не хранит соединения, авторизацию, изменяемый контекст или вычисленные ID.
- Ищи по подтверждённому стабильному ключу. Если доступно только название, уточняй контекст и требуй единственного точного совпадения; не выбирай первую запись. Регион и город могут иметь разные ключи: проверяй связь по контракту, не подменяй один другим.
- Различай отсутствие, неоднозначность, неактивность, отказ доступа и недоступность источника. Ошибка подготовки объясняет причину безопасными данными; не подставляй фиктивный ID или другой вариант и не превращай отсутствие обязательных данных в skip. Допустимость неактивной записи определяется сценарием. Создание или изменение записи требует отдельной подготовки и принятого cleanup.
- Возвращай ID в типе существующего контракта. Кеш добавляй только при необходимости, отдельно от enum, с ключом по окружению, стабильному ключу и применимому контексту tenant/региона; зафиксируй актуальность и инвалидирование.

Например, тест может выбрать город по его стабильному ключу и метаданным; fixture передаёт его вместе с контекстом существующему клиенту и получает единственную подходящую запись с ID этого окружения. Пример не требует географического каталога или конкретных значений в каждом проекте.

## Проверки

Проверяй структуру файлов и корректность импортов, стабильные коды, отсутствие aliases, уникальность ключей составных значений, неизменяемость и различие технического `Enum.name` и доменного названия. Сверяй совместимость строкового enum с фактической версией Python и потребителями.

Для разрешения ID проверяй передачу точного ключа и контекста, разные ID одной записи в разных окружениях/tenants, отсутствие и неоднозначность совпадений, неактивность, отказ доступа и недоступность источника. При наличии кеша проверяй изоляцию и актуальность. Collection не должен обращаться к сети или БД; подменённый клиент/repository проверяет логику и ошибки, но не подтверждает наличие записи и ID на стенде. Реальную интеграцию выполняй только при разрешённом доступе и отдельно сообщай результат.
