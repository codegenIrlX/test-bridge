# Архитектура pytest-фреймворка и проверки

Тест описывает сценарий и ожидаемое поведение; fixtures собирают зависимости и управляют ресурсами. Разделяй
переиспользуемые компоненты фреймворка и исполняемые сценарии. `src` layout допустим по конфигурации, но не обязателен.
Не создавай базовые классы или слои без ответственности и сохраняй действующий layout и контракты.

Для API-фреймворка транспорт управляет HTTP, доменный Client описывает операции API и возвращает исходный ответ.
Успешный UserSteps проверяет ожидаемый статус и DTO; большой доменный BusinessSteps составляет операцию из UserSteps и
возвращает типизированный результат. Междоменные BusinessSteps соединяют операции нескольких доменов. DTO, тестовые
данные и предметные assertions принадлежат домену; конфигурация, отчётность и общие проверки — общим компонентам.
Подробное дерево, границы и cleanup — в [профиле API AQA](project-structure.md). При внедрении в существующий проект
согласуй изменение контрактов: не заменяй возвращаемый HTTP-ответ DTO незаметно для потребителей.

Каждый DTO, включая вложенный, базовый и элемент списка, определяй в отдельном файле по домену и назначению. Сохраняй
aliases и ограничения, добавляй краткий русский docstring и `Field(description=...)` каждому полю Pydantic DTO.

Общие настройки, auth и инфраструктурные fixtures размещай в корневом `tests/conftest.py`, общие для набора — в его
`conftest.py`, доменные — в доменном. Выбирай scope по ресурсу и изоляции, задавай порядок зависимостями; освобождай
ресурсы и при частичном setup до `yield`. Вспомогательная логика принадлежит импортируемым модулям, не импортируй
`conftest.py`.

Не скрывай проверяемое действие в fixture: если тест проверяет создание сущности или login, действие видно в теле
сценария. Для теста другой возможности та же операция может быть подготовкой. Передавай зависимости композиционно через
конструкторы и fixtures; классы оправданы состоянием, жизненным циклом или связанной ответственностью, а не единым
стилем всех helpers.

Статус, DTO и однозначность объекта — критические проверки до зависимых условий. При более чем пяти независимых
смысловых проверках одного результата используй soft assertions; считай условия, а не строки или методы. Отсутствие
вложенного объекта останавливает только зависящие от него обращения. Не скрывай неожиданные исключения и не раскрывай
данные в сообщениях.

Предметные assertions проверяют наблюдаемый результат по независимым ожиданиям и не делают скрытых HTTP/SQL-запросов. Не
подменяй бизнес-проверку одной валидацией DTO; ограничение DTO также не должно мешать намеренно отправить некорректный
запрос в отрицательном тесте.

## Границы подтверждения

- Unit-тест клиента, генератора, auth provider или BusinessSteps с подменой транспорта проверяет сам фреймворк.
- Интеграционный тест взаимодействия с реальным backend проверяет выбранный контракт и поведение в данном окружении.
  Несколько HTTP-вызовов сами по себе не делают сценарий e2e.
- Проверка DTO или mock-ответа не доказывает соответствие работающего backend схеме. In-process тест приложения требует
  его реального кода и настроенного lifecycle; внешний API-проект не превращается автоматически в тесты FastAPI/ASGI.
- Контрактные проверки структуры, статусов и ошибок дополняют бизнес-сценарии. Совпадение с OpenAPI не доказывает
  корректность бизнес-правил, прав доступа и побочных эффектов.

Выбирай границу и ожидаемые результаты до реализации; отмечай реальные и заменённые зависимости в отчёте. Для техники
тестирования используй [паттерны](patterns.md), для измерения собственного кода — [coverage](coverage.md).

## Копируемые ресурсы

Файлы [http_assertions.py](../assets/assertions/http_assertions.py), [dto.py](../assets/assertions/dto.py)
и [soft.py](../assets/assertions/soft.py) можно скопировать в принятый пакет проверок целевого проекта и адаптировать
импорты и синтаксис к его Python. `http_assertions.py` требует HTTPX, `dto.py` — HTTPX и Pydantic 2; `soft.py`
использует стандартную библиотеку. Файлы не импортируют друг друга и не требуют Allure. Проверь совместимость
зависимостей до использования; установка не выполняется автоматически.

Для Allure передавай `step_factory=allure.step` в helper либо `SoftAssertions(step_factory=allure.step)`; без аргумента
шаги работают без отчётности. Заголовки и сообщения должны быть безопасными, не передавай туда credentials или полные
ответы. HTTP и DTO helpers возвращают соответственно `None` и DTO; при невалидном DTO скрываются исходная
ValidationError и тело ответа. Не заменяй опубликованные контракты и принятые helpers без оценки совместимости.
