# Структура API AQA-проекта

Справочник описывает обязанности транспорта, доменных клиентов, шагов, DTO и тестов. Используй дерево при проектировании структуры и адаптируй его к масштабу, контрактам и соглашениям проекта. В существующем проекте сохраняй рабочие импорты и публичные контракты.

## Целевое дерево

Подставь имена пакета, доменов, операций и сценариев своего проекта. Добавляй компоненты по мере необходимости, включая авторизацию, отчётность, справочники и сквозные тесты.

```text
api-tests/
├── AGENTS.md
├── .agents/skills/<выбранные-скиллы>/
├── pyproject.toml
├── pytest.ini                         # либо другая принятая конфигурация pytest
├── .env.example                       # безопасные имена и образцы настроек
├── src/
│   └── <package>/
│       ├── __init__.py
│       ├── core/

│       │   ├── logging.py             # безопасная диагностика
│       │   ├── assertions/

│       │   │   ├── dto.py
│       │   │   └── soft.py
│       │   ├── pagination/            # общий контракт, если он действительно общий
│       │   └── reporting/
│       │       └── steps.py           # адаптер принятой отчётности
│       ├── infrastructure/

│       │   │   ├── token_provider.py
│       │   │   ├── bearer_auth.py
│       │   │   ├── errors.py
│       │   │   └── dto/<операция>/

│       │       ├── dto/<operation>/
```

Добавляй `results.py`, когда операции возвращают составные результаты. Вспомогательную логику отдельного набора можно разместить в `tests/helpers`, а общую доменную логику — в соответствующем домене. Зависимости направляй от тестов к коду фреймворка.

Для нового проекта с этим layout настрой установку пакета и совместимый import mode; не исправляй импорты случайными изменениями `sys.path`. `src` и `importlib` описаны в [рекомендациях pytest](https://docs.pytest.org/en/stable/explanation/goodpractices.html). Версии Python, HTTP-клиент, DTO-библиотека, отчётность и CI определяются проектом, а не названием каталога.

## Ответственности и результаты

| Компонент | Ответственность | Результат |
| --- | --- | --- |
| Transport | HTTP, timeout, соединения, разрешённое назначение, техническая диагностика | Исходный HTTP-ответ или транспортная ошибка |
| Client | Конкретный API-контракт: метод, путь, параметры, сериализация | Исходный HTTP-ответ, в том числе для отрицательных сценариев |
| UserSteps | Отдельное успешное API-действие, ожидаемый статус и проверка DTO | Проверенный DTO; для ответа без тела — предусмотренный контрактом результат |
| Доменный BusinessSteps | Крупная операция одного домена из нескольких UserSteps | Типизированный результат завершённой операции |
| Междоменный BusinessSteps | Композиция больших операций нескольких доменов | Типизированный результат всего сценария |
| Fixture | Сборка зависимостей, предусловия, владение ресурсами и cleanup | Подготовленный объект или контекст |
| Test и предметные assertions | Проверка требуемого поведения и бизнес-результата | Наблюдаемый вердикт сценария |

Типизированный бизнес-результат может быть небольшой `dataclass` с нужными DTO и идентификаторами. Он не является HTTP DTO автоматически. Возвращай фактически необходимые данные; не создавай общий изменяемый dict-контекст, объект со всеми возможными полями или скрыто открытым соединением. Не добавляй HTTP-операцию только ради другого формата возврата.

В существующем проекте UserSteps может возвращать HTTP-ответ, а DTO проверяться отдельно. Переход к целевому контракту требует обновления потребителей и проверок совместимости в согласованном объёме. Отрицательные сценарии используют Client или специальный шаг с явным контрактом ошибки; успешный шаг не должен мешать проверить неверный payload, отказ авторизации или неожиданный статус.

## Доменные и междоменные BusinessSteps

Домен владеет своими `business_steps.py`, DTO, генераторами и assertions. Корневой `business_steps/` содержит только операции, действительно связывающие несколько доменов. Домены не импортируют корневые сценарии; не делай взаимные вызовы доменных шагов, создающие циклы. Зависимости передаются через конструкторы и собираются fixtures. Базовый класс для всех клиентов или шагов не требуется.

Определяй количество и порядок UserSteps по контракту API. Явно передавай результаты и идентификаторы между операциями. Создание новых ресурсов должно быть видно из назначения сценария и его шагов.

Выбирай уровень вызова по цели теста. Отдельный endpoint проверяй через Client или UserSteps. BusinessSteps используй для предусловий или как действие, которое проверяет тест. Выполняй проверяемое действие явно в теле теста.

## Проверки внутри шагов

UserSteps проверяет статус и DTO до зависимых обращений. BusinessSteps проверяет необходимые предусловия и готовность результата к дальнейшим действиям: наличие ID, однозначность объекта, требуемое промежуточное состояние. Если API имеет eventual consistency, используй ограниченное контрактом ожидание с явным условием и диагностикой; не добавляй sleep или polling без необходимости.

Полные предметные ожидания принадлежат тесту и доменным assertions: связи, значения, права и побочные эффекты. Готовый DTO не доказывает правильность бизнес-результата. Assertions не выполняют скрытые запросы; нужное повторное чтение видно в сценарии. Критические проверки и правило soft assertions остаются в [общем справочнике](architecture.md).

## Владение данными и частичный сбой

Определи, кто владеет каждым созданным ресурсом и что передано взаймы. Fixture или другой явный владелец начинает жизненный цикл до первого изменяющего вызова. BusinessSteps регистрирует очистку собственных ресурсов по мере их появления; нельзя ждать успешного завершения всего большого шага и только затем передавать ID для cleanup.

Для синхронного сценария возможен `ExitStack`, открытый fixture до вызова BusinessSteps: шаг регистрирует подтверждённую компенсирующую операцию сразу после получения достоверного ID. Стек закрывается после теста и при ошибке до `yield`; обратный порядок регистрации должен соответствовать зависимостям данных. Для async нужен соответствующий async-механизм. Это вариант реализации, а не обязательный самописный реестр ресурсов.

- Удаляй только ресурсы, которыми владеет сценарий. Очистку заимствованных ресурсов оставляй их владельцу.
- Успешный серверный create с потерянным или невалидным ответом может оставить ресурс без известного ID. Используй только поддерживаемые API ключ идемпотентности, внешнюю метку или точную процедуру сверки; иначе явно сообщи неопределённый остаток. Повтор запроса не является очисткой.
- При отсутствии API удаления зафиксируй согласованную альтернативу: изолированный стенд, reset, срок жизни данных или разрешённое сохранение. Не придумывай delete endpoints и не обещай rollback внешнего сценария.
- Cleanup выполняется и при частичном setup; ошибки очистки не подавляются и не должны терять сведения о первичном сбое. Проверь поведение принятого отчётчика для обеих ошибок.
- Параллельные workers используют независимые ресурсы или явную координацию. Общая session-fixture одного процесса не создаёт глобального владельца всех workers.

## Проверка внедрения

Проверь импорты и отсутствие сетевой активности при collection. Локально проверь сборку зависимостей, типы результатов, отказ промежуточного шага, очистку после частичного создания и сохранение заимствованных ресурсов. Реальная проверка backend-контракта, auth, побочных эффектов и cleanup выполняется отдельно на разрешённом стенде; mock этих свойств не доказывает.
