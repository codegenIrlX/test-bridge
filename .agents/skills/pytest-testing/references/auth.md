# Авторизация в pytest-тестах

Эти правила относятся к тестовому клиенту и fixtures, а не к построению системы авторизации приложения. Прежде изучи существующие контракты, роли identity provider, окружения, источники credentials, клиент и поддерживаемые потоки. Сохраняй принятые интерфейсы; не придумывай роли, scopes и endpoints.

## Выбор механизма и ответственность

- Bearer — способ предъявления, JWT — возможный формат токена, OAuth2 — протокол; они не взаимозаменяемы. Для передачи токена декодирование JWT не требуется, непроверенные claims не подтверждают identity или права.
- Для готового Bearer token применяй предусмотренный адаптер. Для login/password выполняй фактический JSON/form-контракт и учитывай cookies, CSRF и logout. Для cookie session изолируй cookie jar каждой identity. Для Basic Auth и API key используй предусмотренный механизм клиента, защищённый транспорт и разрешённый header.
- OAuth2 client credentials подходит для предусмотренной сервисной identity и не доказывает пользовательский сценарий. Пользовательский OAuth/OIDC flow выполняй по контракту провайдера; для подходящего клиента рассматривай Authorization Code с PKCE. Не обходи MFA или consent и не выбирай Resource Owner Password Credentials для новой OAuth-интеграции; legacy flow не меняй без отдельного решения.
- Auth client вызывает имеющиеся login, refresh и logout/revoke; provider владеет состоянием identity и обновлением; адаптер предъявляет credentials; fixtures создают и освобождают ресурсы. Это обязанности, а не обязательные четыре класса: для статического токена достаточно подходящего адаптера и fixture.
- Предъявляй credentials только разрешённому назначению по транспортной политике проекта. Не помещай секреты в URL или аргументы команд; ограничивай передачу credentials при переходе на другой origin и неразрешённом redirect.

## Fixtures и безопасность

- Для обычного бизнес-теста fixture подготавливает необходимый авторизованный контекст до передачи управления тесту. Ошибка обязательной авторизации останавливает setup; пустая или отсутствующая обязательная настройка — безопасная ошибка, не skip и не рабочий default. Не делай login при импорте, collection или общей autouse-фикстурой для всех тестов.
- Когда тест проверяет сам login, refresh или отказ, выполняй действие в сценарии. Для тестов без credentials и с невалидными credentials используй отдельный клиент без скрытого добавления, обновления или восстановления авторизации.
- Выбирай scope по изоляции пользователей, environments и mutable состояния. Явно определи владельца клиента, cookie jar, сессии и необходимого logout/revoke; освобождай уже полученные ресурсы и при ошибке до `yield`. Не удаляй чужие данные и не подавляй ошибки cleanup.
- Получай настройки через принятый в проекте механизм; не вводи loader или secret manager ради примера. Не раскрывай credentials в логах, параметрах, ids, именах тестов, repr, ошибках, JUnit, Allure results или attachments. Маскирование консоли CI не гарантирует защиту артефактов.
- При наличии Allure отражай фактические login и refresh отдельными безопасными шагами с одним владельцем каждого шага; не собирай аргументы, токены и результаты автоматически. Не добавляй Allure только ради этого правила.

## Истечение, обновление и конкурентность

- Различай относительный TTL и абсолютное истечение: для относительного времени используй монотонные часы, для абсолютного — время эпохи. Запас и clock skew определяй по контракту; в unit-проверках управляй часами.
- Если refresh ротирует access/refresh-пару, валидируй ответ до атомарной замены всей пары и связанных сроков. При отсутствии нового refresh token следуй контракту провайдера; ошибка или неполный ответ не должны оставлять смешанное состояние. Не переходи молча к старому токену, другой identity или повторному login.
- Синхронизируй конкурентный refresh и доступ к состоянию; lock одного процесса не координирует workers pytest-xdist. Для процессов используй независимые сессии/credentials либо явную координацию, учитывая ротацию и ограничения провайдера. Ключ кэша учитывает identity, environment, client, scopes, audience и применимый tenant.
- Не выполняй бесконечный refresh или автоматический повтор любого `401`. Бизнес-POST и другие операции повторяй только по явной политике повторного выполнения с учётом идемпотентности и состояния запроса; в негативных auth-тестах скрытый повтор недопустим.

## Проверки и границы подтверждения

По существующему контракту выбирай успешный доступ и отказ: отсутствие, неверные и истёкшие credentials, недостаточные права, чужие объекты и tenant-изоляцию при наличии. Проверяй фактические status и headers, а также отсутствие изменения данных при отказе; не назначай универсальный ответ вместо контракта.

Если механизмы существуют, проверяй срок действия, refresh, отсутствие частичной ротации и fallback, согласованность параллельного обновления и изоляцию между тестами и workers. Проверяй, что клиент не отправляет credentials чужому origin или при запрещённом redirect и не повторяет POST без разрешённой политики. Искусственные маркеры секретов ищи в logs, results, JUnit и attachments, когда такие артефакты фактически создаются.

Unit-тест адаптера и mocked login не доказывают реальный flow и работу identity provider; наличие токена не подтверждает права. Identity override в component-тесте не проверяет login или credentials. В отчёте различай реальные проверки, подмены и недоступные интеграции; фактическую безопасность отчётов подтверждает только проверка созданных артефактов.
