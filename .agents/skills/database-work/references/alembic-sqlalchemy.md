# Alembic и SQLAlchemy

Применяй эти рекомендации в проектах с Alembic или SQLAlchemy. Семь практик
адаптированы из [статьи Павла Логинова](https://medium.com/@pavel.loginov.dev/best-practices-for-alembic-and-sqlalchemy-73e4c8a6c205).

## Имена и описания

- **Имена ограничений и индексов.** Используй принятую в проекте
  `MetaData.naming_convention` для PK, FK, UNIQUE, CHECK и индексов. При
  автогенерации передавай объект `MetaData` в `target_metadata`. При вводе
  соглашения учитывай фактические имена объектов в БД. [Именование в Alembic](https://alembic.sqlalchemy.org/en/latest/naming.html).
- **Даты в именах файлов.** При необходимости настрой `file_template` так,
  чтобы файлы сортировались по дате и по имени были видны ID ревизии и краткое
  описание. Порядок выполнения задаёт граф ревизий. [Шаблон имени](https://alembic.sqlalchemy.org/en/latest/tutorial.html), [граф ревизий](https://alembic.sqlalchemy.org/en/latest/branches.html).
- **Комментарии.** Описывай назначение таблиц и колонок через `comment` в
  SQLAlchemy и сохраняй описания в схеме БД через миграции. В сообщении
  ревизии (`-m`) указывай конкретное изменение, например «Добавить время
  завершения импорта».

## Содержание и проверка миграций

- **Независимость ревизий от текущих моделей.** Для небольших преобразований
  используй SQL или локальное описание таблицы через `sa.table()` и
  `sa.column()`. Имена и типы должны соответствовать схеме на момент выполнения
  ревизии. Для объёмного заполнения данных используй отдельный шаг, который
  можно безопасно продолжить или повторить. Проверь заполнение до введения
  ограничения или удаления старой колонки. [Миграции данных](https://alembic.sqlalchemy.org/en/latest/cookbook.html#data-migrations-general-techniques).
- **Stairway-тест.** Для обратимой ревизии пройди
  `upgrade → downgrade → upgrade` от её родителя на изолированной БД и проверь
  схему и затронутые данные после переходов. Отдельно проверь цепочку на пустой
  БД и обновление с предыдущей поддерживаемой версии с данными. Для необратимого
  преобразования явно укажи ограничение отката и опиши способ восстановления,
  например из проверенной резервной копии.
- **Отдельный запуск миграций.** Выполняй миграции отдельной командой или
  сервисом после готовности БД. Запускай приложение после успешного завершения
  миграции. В Compose эти условия задают `service_healthy` и
  `service_completed_successfully`. [Порядок запуска в Compose](https://docs.docker.com/compose/how-tos/startup-order/).
- Проверяй результат `--autogenerate` вручную. При переименовании Alembic может
  предложить удалить старую колонку и добавить новую. Замени операции на явное
  переименование и проверь сохранность значений. Сверяй ограничения, индексы
  и серверные значения по умолчанию с фактической схемой. [Ограничения автогенерации](https://alembic.sqlalchemy.org/en/latest/autogenerate.html).

## Модели и сессии

- **Mixins.** Выноси повторяющиеся поля, например UUID или метки времени, если
  совпадают их назначение и правила заполнения. `default` и `onupdate` действуют
  при выполнении соответствующих операций через SQLAlchemy. Если значение
  должна формировать БД для всех клиентов, задай это в схеме, например через
  `server_default` для вставки. [Mixins](https://docs.sqlalchemy.org/en/20/orm/declarative_mixins.html), [значения по умолчанию](https://docs.sqlalchemy.org/en/20/core/defaults.html).
- Ограничивай жизнь сессии операцией и управляй транзакцией на её внешней
  границе. Создавай отдельную `AsyncSession` для каждой параллельной задачи.
  [Сессии SQLAlchemy](https://docs.sqlalchemy.org/en/20/orm/session_basics.html), [AsyncSession](https://docs.sqlalchemy.org/en/20/orm/extensions/asyncio.html#using-asyncsession-with-concurrent-tasks).
